Linux 文件与 I/O

三个问题：为什么说「一切皆文件」？一次 write() 的数据要走过哪几层才真正到磁盘？阻塞、非阻塞、epoll、io_uring 到底差在哪？

生活比喻：寄快递

写数据就像寄包裹。你把东西交出去的那一刻（write() 返回），包裹只是放进了小区快递柜，离收件人（磁盘）还远着呢。

① 一切皆文件：一套接口，什么都能读写

「文件」在 Linux 里不只是硬盘上的文档，而是一个能 open / read / write / close 的东西。打开后内核给你一个小整数叫文件描述符 fd（大白话：取件号），之后都凭号办事。

顺便记住两件事

读是反过来的：read() 先查 Page Cache，命中就直接从内存拷给你（所以同一个文件第二次读飞快）；没命中才一路向下发请求，读回来顺便留一份在 Page Cache。

O_DIRECT：打开文件时加这个标志，会绕过 Page Cache 直接走文件系统→块层。数据库常这么做，因为它们自己管缓存，不想多存一份。

③ 阻塞、非阻塞、epoll、io_uring

场景：一个线程要服务 4 个网络连接 A、B、C、D，它们的数据在不同时刻到达（B 第 2 格、C 第 3 格、A 第 6 格、D 第 9 格）。看四种做法下，这个线程每一格时间在干什么。

餐厅取餐比喻
阻塞站在 1 号窗口死等，别的窗口好了也不管
非阻塞不停挨个窗口问「好了没？」腿都跑断
epoll领个取餐器，响了告诉你哪几份好了，你自己去端
io_uring下单时留好餐盘，做好了直接送到桌上

线程在处理数据 睡着等（不占 CPU） 空转（白烧 CPU） 提交请求 数据到达 数据到了却没人管

关键分水岭：「就绪通知」vs「完成通知」

epoll 说的是「可以读了」——你还得自己调 read()，由你的线程把数据从内核拷出来。所以 epoll 仍属于同步 I/O，只是把「等」集中到一处。

io_uring 说的是「读好了」——你事先把请求和缓冲区放进提交队列 SQ，内核做完后把结果放进完成队列 CQ。两个队列是用户态和内核共享的内存环，取结果不用系统调用。这才是真正的异步 I/O。

模型没数据时线程内核告诉你一个线程管多少连接能用于普通磁盘文件？
阻塞睡在 read 上（直接返回数据）1 个，要多开线程能，但会卡住
非阻塞立刻得到 EAGAIN，自己反复问没好 / 好了多个，但空转费 CPU没效果，磁盘文件总被当成「就绪」
epoll睡在 epoll_wait 上哪些 fd 就绪成千上万不支持（epoll_ctl 返回 EPERM）
io_uring睡在 io_uring_enter 上（或完全不睡）哪些请求已完成 + 结果成千上万能，真正异步读写文件

常见误区

✗ write() 成功 = 数据在磁盘上了
只是进了 Page Cache（内存）。要确保落盘得调 fsync()/fdatasync()。
✗ fflush() 就是刷到磁盘
fflush 只把 libc 用户缓冲区交给内核（调 write），到 Page Cache 为止。
✗ 非阻塞 = 异步
非阻塞只是「不睡」，数据还是你自己 read 拷；epoll 也是同步的。只有 io_uring（以及老的 Linux AIO）是完成通知式异步。
一句话总结：Linux 用 fd 把万物统一成「文件」；写入先停在 Page Cache，靠回写或 fsync 才穿过文件系统、块层、驱动落盘；阻塞是干等，非阻塞是瞎问，epoll 是「好了叫你自己来拿」，io_uring 是「做好了送上门」。
